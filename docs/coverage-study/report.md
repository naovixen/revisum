# Coverage study

## Sample

- Date: 2026-10-29. Plan language 1.3, with each suite's project enabling only the unsafe features its expressible intents need. Files read at the pinned commit linked from each intent. See `rerun-1.3.md` for what changed, and `rerun-1.2.md` for the closed-language re-run.
- Suites (10): Cal.com, Grafana, Supabase Studio, Rocket.Chat, Saleor Dashboard and WordPress Gutenberg (Playwright); Mattermost (Cypress); MediaWiki (WebdriverIO); OpenProject (Capybara with Selenium); Cypress Real World App (Cypress, the one demo app).
- Original sample (100, ten per suite): in each suite's main end-to-end folder, spec files in alphabetical order and the first test of each, skipped ones included. Where a folder has fewer than ten files (MediaWiki, Real World App), the second test of each file from the top.
- Fresh sample (50, five per suite): the same rule continued. The next five spec files after those already used, first test of each. MediaWiki and the Real World App continue with the next unused test of each file from the top (the second, then the third). Drawn and judged before any language change.
- Judging rules (strict, as for 1.2):
  - A test is expressible only if every step is, its setup and teardown hooks included. A weaker check standing in for the original does not count.
  - Standing preconditions count: test accounts, settings, feature switches, plugins, themes, extensions, the demo app's fixed seed data and their resets.
  - Declared service calls count for setup, cleanup or backend checks only when the suite's own test or helpers already call that HTTP endpoint; the reason cites the file.
  - Declared stubs and request checks count for fetch or XHR traffic with data responses. Storage counts for local or session storage keys the test reads or writes directly.
- Added for the unsafe features, strictly, without the design projection's generous assumptions:
  - An unsafe feature counts only when it reproduces what the original test does. A CSS or XPath locator counts for the selector the test itself uses; it never replaces a role, label or text lookup, a record id read from the page, or a key press at the current focus.
  - A declared page script counts only for the same script or storage logic the test runs in the page, such as the suite's `editor.insertBlock` helper. It never stands in for test code, a user action or a cookie.
  - A database command counts only where the suite's own setup runs that query or command and it can be declared as a fixed argument vector. Factories, Prisma calls in test code and writes with per-run keys do not count.
- A plan using an unsafe feature counts only toward the "1.3 with unsafe features" share; the closed share and the kill criterion are unchanged. Features whose driver parts are not built still count; their reasons say "needs SPEC-36 driver parts" (or SPEC-06's, or SPEC-07's service caller).
- Each suite has its own project in `intents.json`, declaring only what that suite's tests evidence. Every expressible plan parses under it.
- This section is added by hand; rerunning the tool removes it.

## In short

- 150 test intents from 10 suites; 68 expressible in the closed plan language (45.3%).
- 1.3 with unsafe features, where each suite's project enables them: 78 expressible (52.0%).
- The original sample: 100 intents, 50.0% expressible in the closed language, 56.0% in 1.3 with unsafe features.
- The fresh sample: 50 intents, 36.0% expressible in the closed language, 44.0% in 1.3 with unsafe features.
- The MVP plan's kill criterion is 70% expressible in the closed language: not met.
- An intent marked expressible counts only when its plan passes the plan parser under its suite's project. A plan using an unsafe feature counts only toward the second share.
- Generated by `node tools/coverage-study.ts` from `docs/coverage-study/intents.json`. Do not edit by hand.
